# ANSWERS.md — Netra-One Systems Questions

## Q1. Zero-Copy RTSP Ingestion at Scale (16–50 Cameras)

`cv2.VideoCapture` commonly decodes H.264/H.265 in software and converts decoded YUV frames to BGR on the CPU. A 1920×1080 BGR frame is about 6.22 MB; at 32 cameras × 30 FPS, that is roughly 6 GB/s of raw pixel traffic before intermediate copies, preprocessing, or model transfers. The practical failure is usually not just PCIe bandwidth: it is CPU decode/conversion cost, memory bandwidth, thread scheduling, and jitter when several readers contend for cores. If the inference worker waits on each reader in sequence, one slow camera can also delay every other camera.

A hardware-decoded pipeline such as DeepStream/GStreamer (`rtspsrc → nvv4l2decoder → nvstreammux → nvinfer`) uses NVDEC and can retain decoded frames in GPU-visible NVMM memory. This can avoid a full raw-frame round trip through host RAM and batch frames across cameras. In Python, PyNvVideoCodec can expose decoded device buffers to CUDA consumers, depending on the integration. Decoded frames can stay on the device when downstream operators support that memory type. Capacity must still be sized by codec, resolution, frame rate, decoder throughput/session limits, inference cost, and network jitter. A latest-frame queue remains useful because hardware decoding does not prevent downstream inference from falling behind.

## Q2. TensorRT Dynamic Batching vs. Fixed-Shape Engines

TensorRT optimization profiles specify minimum, optimum, and maximum dimensions. The builder selects tactics using the profile's optimum dimensions, while runtime shapes must remain within the profile. Workspace and activation memory can grow with the maximum shape, so an unnecessarily wide profile can increase memory demand and may produce less suitable tactics for the common batch size. A single profile does not guarantee equally good latency at every batch size.

For four camera streams, I would use a small set of batch buckets such as 1, 2, and 4, with profiles tuned to actual traffic and execution contexts prepared before live traffic. A collector would wait only a short, bounded interval for additional frames, then dispatch the closest supported bucket. Padding a partial batch can stabilize shapes but wastes compute; dynamic shapes reduce padding at the cost of extra shape management and potentially more tactic/workspace variation. Benchmark both approaches with the same input distribution rather than assuming one is faster.

Warm every deployed shape at startup, reuse buffers and contexts, and avoid building engines in the live path. CUDA graphs may reduce launch overhead for stable shapes, but each graph must correspond to a compatible execution shape and buffer lifetime. Under a hard memory budget, set the profile maximum to a realistic upper bound and measure peak memory including contexts, workspaces, and both models.

## Q3. INT8 Calibration & Small-Object Accuracy Degradation

INT8 post-training quantization represents activations with a finite set of levels. If a calibration set is dominated by large, high-contrast objects, its activation ranges may poorly represent faint features from small objects. Quantization error can then erase weak responses in early feature maps or shift box-regression outputs. A small localization error is proportionally more damaging to a 16-pixel object than to a 200-pixel object, and class scores near the confidence threshold can fall below it. Concatenated feature branches with different activation distributions are another sensitivity point.

I would calibrate on representative camera frames: day/night, low contrast, motion blur, crowded scenes, and small objects near the image boundary. Evaluate per-size recall/AP, not just aggregate mAP. Compare FP32/FP16 and INT8 outputs on the same validation set, and inspect layers that disproportionately reduce small-object recall. If the toolchain supports it, keep sensitive detection-head or feature-pyramid operations in FP16 while quantizing less sensitive layers; otherwise consider quantization-aware training. Tune confidence thresholds only after measuring precision/recall trade-offs. INT8 should be enabled only when the measured speed or memory benefit is worth the accuracy change for the intended camera workload. The current default benchmark does not claim INT8 inference or an INT8 accuracy evaluation.

## Q4. Sub-20 ms Model Hot-Swapping Under a Fixed 20 GB VRAM Ceiling

First check whether the requirement is physically feasible. If 14 GB must remain resident, only 6 GB is free. A 4.5 GB incident model plus 1.5 GB of activations consumes that entire remainder, leaving no margin for workspace, CUDA context, fragmentation, or concurrent requests. Loading 4.5 GB of weights across PCIe cannot reliably finish in 20 ms: even at an idealized 25 GB/s, the transfer alone is about 180 ms. A cold, unpredictable swap therefore cannot honestly be guaranteed below 20 ms.

To keep the 30 FPS pipeline responsive, do not block its inference worker on model deserialization or allocation. Prefer keeping the likely incident model resident when the budget allows. Otherwise, pre-build engines and contexts, retain serialized weights in pinned host memory, and start asynchronous transfer on a lower-priority copy stream as soon as a precursor signal gives enough lead time. Use CUDA events to prevent the new model's first kernel from running before its weights are ready. Keep allocations pooled rather than calling `cudaMalloc`/`cudaFree` on the critical path. If there is insufficient VRAM or no warning interval, queue the incident task or run a smaller quantized model; report cold-load latency separately. The sub-20 ms target is plausible for a preloaded/ready model switch, not an arbitrary cold load of multi-gigabyte weights.
